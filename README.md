# Iris classifier в Triton

В проекте `RandomForestClassifier` запускается через Triton Inference Server с Python backend. Модель работает на CPU, принимает массив `FP32` формы `[N, 4]` и возвращает номера классов Iris в формате `INT64`.

## Запуск сервера

```bash
docker build -t triton-iris .
docker run --rm --name triton-iris-server \
  -p 8000:8000 -p 8002:8002 \
  -v "$PWD/model_repository:/models:ro" \
  triton-iris
```

Сервер готов к работе после появления статуса `READY`. Порт `8000` используется для HTTP-запросов, `8002` — для метрик.

## Проверка модели

Во втором терминале:

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r requirements-client.txt
python3 client.py
```

Клиент проверяет классы `0`, `1`, `2` для запросов с 1, 4 и 8 объектами. После применения итоговой конфигурации выполнено 90 из 90 успешных запросов.

## Кастомные метрики

```bash
curl -s http://localhost:8002/metrics \
  | grep -E 'iris_processing_seconds_total|iris_requests|nv_inference_pending_request_count'
```

В модели реализованы две метрики:

- `iris_processing_seconds_total` — суммарное время обработки запросов;
- `iris_requests` — число запросов, которые модель обрабатывает в данный момент.

Во время нагрузочного теста счётчик времени вырос с 3,73 до 101,06 секунды и не уменьшался. При concurrency 32 в очереди было зафиксировано 31 ожидающее обращение.

## Performance Analyzer

При работающем сервере:

```bash
bash profiling/run_perf.sh
```

Проверялись значения concurrency 1, 8, 16 и 32, а также запросы с 1, 4 и 8 объектами. Triton batching отключён (`max_batch_size: 0`), поэтому количество объектов задаётся формой входа `INPUT:N,4`.

| Объектов в запросе | Concurrency | Запросов/с | Объектов/с | p95, мс | Очередь, мс |
|---:|---:|---:|---:|---:|---:|
| 1 | 1 | 159,8 | 159,8 | 7,3 | 0,04 |
| 1 | 8 | 177,6 | 177,6 | 50,8 | 38,7 |
| 1 | 16 | 173,8 | 173,8 | 110,0 | 85,4 |
| 1 | 32 | 172,8 | 172,8 | 205,1 | 177,2 |
| 4 | 1 | 144,5 | 578,1 | 8,8 | 0,04 |
| 8 | 1 | 134,5 | 1076,3 | 9,9 | 0,04 |

После concurrency 8 скорость почти не растёт, а время ожидания в очереди продолжает увеличиваться. Передача нескольких объектов одним запросом эффективнее: для восьми объектов получилось 1076 объектов/с уже при concurrency 1. Полная таблица находится в `results/perf-summary.csv`.

## Model Analyzer

```bash
bash profiling/run_model.sh
```

Для Model Analyzer используется отдельный образ `Dockerfile.model-analyzer`. Он содержит те же зависимости модели и нужен только на время профилирования. Конфиг сравнивает один и два CPU-экземпляра при concurrency 1, 8, 16 и 32.

| Экземпляров | Concurrency | Запросов/с | p99, мс |
|---:|---:|---:|---:|
| 1 | 1 | 184,0 | 6,2 |
| 2 | 1 | 159,5 | 8,0 |
| 1 | 8 | 189,0 | 53,6 |
| 2 | 8 | 221,6 | 55,9 |
| 1 | 32 | 188,7 | 193,4 |
| 2 | 32 | 334,3 | 149,3 |

На небольшой нагрузке второй экземпляр преимущества не дал. При concurrency 32 пропускная способность выросла с 188,7 до 334,3 запроса/с, а p99 уменьшилась с 193,4 до 149,3 мс. Поэтому в итоговом `config.pbtxt` используются два CPU-экземпляра. Исходные результаты находятся в `results/model-analyzer/metrics-model-inference.csv`.

## Вывод

Сервер корректно обрабатывает HTTP-запросы, обе кастомные метрики работают. Для одного экземпляра модели увеличивать concurrency выше 8 невыгодно: запросы дольше стоят в очереди, а throughput почти не меняется. Пакетная передача объектов повышает общую производительность. Для высокой нагрузки лучший результат показала конфигурация с двумя CPU-экземплярами.
